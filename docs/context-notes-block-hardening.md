# 차단 강화 — 틱톡 아이디·IP·접속 기록 (2026-08-14)

## 왜 했나

K 가 `jhtps2@gmail.com` 차단을 다시 요청했다. 이미 KV 목록에 있었는데도 그 사람이 계속 쓰고 있었다.
파 보니 **KV 목록은 워커 API 만 막고, 앱 로그인은 Supabase 라 계정이 살아 있으면 그대로 쓴다**.
게다가 ban 을 걸어도 **이미 발급된 세션/리프레시 토큰은 살아 있다**(자세한 건 context-notes-blocked-emails.md).

그리고 더 큰 구멍 — **이메일은 얼마든지 새로 만들 수 있다.** 차단해도 새 지메일로 돌아오면 그만이다.

## 이번에 만든 것

### 1. 접속 기록 (`public.connect_logs`) — 가장 시급했다

IP 가 Discord 알림에만 찍히고 **어디에도 저장되지 않았다**. 그래서 차단하려 할 때 그 사람 IP 를
우리 쪽에서 알 방법이 없었다. 실제로 이번에 세션을 지우면서 `auth.sessions.ip` 까지 같이 날아갔고
(그게 유일한 조회 가능 소스였다) 세 계정의 IP 를 영영 잃었다. `auth.audit_log_entries` 는 비어 있고
`presence:{userId}` 는 TTL 12분이라 소용없다.

→ 워커 `/ping` 이 **알림 발사 시점에만** 기록한다(하트비트는 제외 — 5분마다 쌓이면 폭증).
RLS 켜고 anon/authenticated 권한 회수, 서비스 롤만 읽고 쓴다. 기록 실패는 조용히 넘어간다
(기록은 부가 기능이고 접속 알림이 본 기능이다).

`user_id` 컬럼은 uuid 인데 토큰이 없으면 워커가 IP 를 userId 로 쓴다 → uuid 형식이 아니면 null 로 넣는다.

### 2. 틱톡 아이디 차단 (주력)

방송인은 지메일은 버려도 **틱톡 계정은 못 버린다**(팔로워·방송 이력이 자산). 앱이 이미
`X-Tikke-Tiktok-Id` 를 매 접속마다 보낸다.

- KV `blockedTiktokIds`
- `requireAuth` 에서 이메일과 **함께** 판정 → 새 지메일로 갈아타도 워커 API 전반이 막힌다.
- `/ping` 초입에서도 차단 → presence(온라인 목록)와 접속 알림이 오염되지 않는다.
- `@` 접두어와 대소문자를 벗겨 비교한다(관리자가 `@id` 로 붙여 넣어도 걸리게).

### 3. IP 차단 (보조)

**`blocked:{ip}` 를 재사용하면 안 된다.** 그건 rate limiter 키고 1시간 TTL 로 계속 덮어써서
영구 차단이 조용히 풀린다. 별도 키 `blockedIps` 를 만들어 최상단 게이트에서 같이 조회한다.

한계를 알고 써야 한다 — 한국 가정용 IP 는 유동이라 며칠이면 풀리고, 모바일은 NAT 라 잘못 넣으면
무고한 사용자가 같이 막히고, VPN 이면 즉시 우회된다. 과속방지턱이지 답이 아니다.

### 4. 관리·역추적 엔드포인트 (ADMIN_SECRET 전용)

```
GET    /blocked/list                          → {emails, tiktokIds, ips}
POST   /blocked   {email|tiktokId|ip}
DELETE /blocked   {email|tiktokId|ip}
GET    /blocked/lookup?email=|ip=|tiktokId=   → 접속 기록 역추적(최근 100건)
```

기존 `{email}` 호출과 `emails` 응답 키는 그대로 둔다(하위호환).
공개 check 엔드포인트는 여전히 두지 않는다 — 차단 대상이 자기 상태를 조회하면 우회 시점을 알게 된다.

## 곁다리로 고친 것 — 구글 로그인 알림 누락

K 제보. 원인은 `if (tiktokId) {...} else { 로그인 알림 }` 구조였다.
앱을 켜면 틱톡 자동 재연결이 먼저 붙는 일이 많은데, 그러면 ping 에 틱톡 아이디가 실려
**로그인 분기를 아예 안 탄다**. 게다가 그 틱톡 알림마저 6시간 dedup 에 걸려 스킵되면 **아무 알림도 안 간다**.
→ 로그인 알림을 틱톡 연결 여부와 **독립**으로 판정한다(각자 dedup: 로그인 1시간, 틱톡 6시간).
로그인 사실과 방송 연결 사실은 서로 다른 정보라 둘 다 와야 한다.

## 검증

`scratchpad/blocktest/run.mjs` — auth.ts 와 blocked.ts 를 esbuild 로 번들해 메모리 KV 로 실제 실행.

- 정규화: `dkrtf8` / `@dkrtf8` / `DKRTF8` 모두 차단, 무관한 값·빈 값은 통과.
- **KV 장애 시 fail open**: 전부 false(전체 사용자가 막히는 게 훨씬 나쁘다). 단 하드코딩 목록은 그대로 차단.
- 관리 라우트: 권한 없음 403, 추가/중복/해제/빈 body 400, 세 종류 독립 동작.
- 라우트로 넣은 값이 판정 함수에 실제로 걸리는지까지 확인(연동).

## 앱 안 관리 화면 (AdminBlocked)

K 가 실시간으로 직접 넣고 빼도록 기존 "차단 계정" 화면을 확장했다(개발 빌드 전용, 배포 불필요).

- **종류 탭**: 이메일 / 틱톡 아이디 / IP. 각 탭에 현재 개수와 성격 설명을 붙였다
  (이메일은 갈아타면 그만, 틱톡은 가장 확실, IP 는 유동·NAT 라 보조).
- **입력 정규화**: 틱톡은 `@` 를 벗기고 소문자로, 이메일도 소문자로. IPv6 도 받는다(실제로 IPv6 로 찍히는 접속이 있다).
- **접속 기록 찾기**: 이메일로 그 사람 IP 를, IP 로 그 주소를 쓴 계정을 조회한다(최근 100건).
  각 행의 "IP 넣기" 버튼이 그 IP 를 차단 입력창에 바로 채운다 — 디스코드를 뒤질 필요가 없어진다.
- IPC 는 `kind` 를 안 넘기면 이메일로 동작한다(구버전 화면 하위호환).

**주의**: 접속 기록은 이 기능이 **배포된 뒤의 접속부터** 쌓인다. 그전 기록은 없다(그래서 화면에도 그렇게 적어 뒀다).

# 틱톡 연결 알림 누락 — 키를 먼저 쓰고 보낸 게 원인 (2026-08-15)

## 증상

K: 틱톡 계정 연결 알림이 간헐적으로 안 온다.

## 왜 "간헐적"이고 왜 "영구"인가

```js
// 예전 코드
await put(alertKey, "1", { expirationTtl: 6시간 });   // ← 키 먼저
await sendDiscordAlert(...);                          // ← 그 다음 전송
```

전송이 실패하거나 `ctx.waitUntil` 이 잘리면 **키만 남는다**. 그러면 그 사용자는 6시간 동안 침묵인데,
**하트비트(5분)가 그 키의 수명을 계속 연장**한다 → 앱을 켜 두는 한 침묵이 **영구화**된다.
다른 사용자는 멀쩡히 알림이 오므로 "간헐적"으로 보인다.

`discord:last_error` 가 비어 있다고 안심하면 안 된다 — waitUntil 이 잘리면 예외가 없어서
`stamp()` 자체가 안 돈다. 그리고 `discord:last_ok` 는 타입 구분이 없어서 나중에 온 LOGIN 이
TIKTOK_CONNECTED 를 덮어쓴다(그래서 이번에 판별이 안 됐다).

**dedup 키가 있다 ≠ 알림이 갔다.** 이걸 증거로 쓰면 안 된다.

## 고친 것

1. `sendDiscordAlert` 가 **성공 여부를 반환**한다(`res.ok`).
2. **보낸 뒤에** dedup 키를 쓴다(틱톡·로그인 양쪽). 실패하면 키를 안 남기니 다음 ping 이 다시 시도한다.
   - 대가: 동시 ping 두 건이 둘 다 "키 없음"을 보면 알림이 중복될 수 있다. 영구 침묵보다 낫다.
3. `logConnect` 를 **알림 뒤로** 옮겼다. 2026-08-14 에 알림 앞에 넣었는데, 그러면 Supabase 왕복이
   알림보다 먼저 걸려 waitUntil 이 잘릴 때 알림을 통째로 잃는다(신고 시점과 정확히 맞는다).
   기록은 부가 기능이고 알림이 본 기능이다 — 순서가 그 원칙과 반대였다.
4. 진단용으로 `discord:last_ok:{TYPE}` / `discord:last_error:{TYPE}` 도 같이 남긴다.
   이제 "틱톡 알림은 언제 마지막으로 성공했나"를 바로 읽을 수 있다.

## 배포 후 할 일

이미 잘못 남은 `tiktok_connected:*` 키는 그 사용자를 계속 침묵시킨다 → **배포 뒤 삭제**해야
다음 접속 때 알림이 되살아난다. (배포 전에 지우면 구버전 워커가 또 키부터 쓴다.)
