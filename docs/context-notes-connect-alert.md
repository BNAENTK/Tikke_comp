# 접속 알림에 이름·이메일이 빠지던 것 (2026-08-13)

K 제보(스샷): 틱톡 연결 알림이 `이름 (없음) / 이메일 (없음) / 틱톡 아이디 dkrtf8 / IP` 로 온다. "또" 반복됨.

## 먼저 확인한 것 — K 본인 계정 문제가 아니다

K 앱 DB(`app_settings`)의 access/refresh 토큰은 정상이고 JWT 안에 email·full_name·sub 다 있고 유효했다.
즉 알림의 주인공은 **다른 사용자**이고, 그쪽 앱이 `Authorization` 헤더를 안 실어 보낸 것이다.

## 비로그인이 아니라 버그다

`App.tsx` 는 `if (!session) return <Login />` — **로그인해야 연결 화면 자체에 못 간다.**
그러므로 "틱톡 아이디는 왔는데 토큰이 없다"는 정상 상태가 아니다.

원인은 **메인 프로세스 세션 드리프트**다. 앱 시작 시 `index.ts` 가 `restoreSession()` 으로 메인 클라이언트에
세션을 넣는데(`persistSession:false` 라 수동), 이게 네트워크 오류로 한 번 실패하면 저장 토큰은 그대로 두고
넘어간다 → **그 실행 내내 메인 세션이 빈 채로 남는다**. 렌더러는 자기 세션으로 계속 로그인 상태를 보여주니
아무도 눈치채지 못한다.

경로별로 갈린다:
- `ipc.ts:957` (`tikke:connect:ping`) — 렌더러가 토큰을 넘겨줘서 **멀쩡**.
- `live-connect.ts:23/81` (틱톡/유튜브 연결 직후), `ping.ts` 하트비트 — 메인 세션에 의존해서 **토큰이 빠진다**.

이 비대칭이 "간헐적으로 이름 없는 알림"의 정체다.

## 고친 방식 — 보내기 **전에** 채운다

`pingWorker` 에서 `getSession()` 이 비면 `loadStoredTokens()` → `restoreSession()` 을 한 번 하고 그 다음 보낸다.

**보내고 나서 재시도하면 안 된다.** 워커의 dedup 키가 `tiktok_connected:{userId}:{tiktokId}` 인데
`userId = payload.sub ?? clientIp` 라, 토큰 없는 ping 은 IP 키를, 토큰 있는 ping 은 sub 키를 점유한다 →
같은 연결에 알림이 **두 번** 나간다. 그래서 첫 요청 전에 토큰을 확보하는 형태여야 한다.

복원 과정에서 토큰이 회전될 수 있어 `saveSession()` 도 부른다(안 하면 다음 실행이 옛 refresh 토큰으로 또 실패).

## 검증 — ping.ts 를 esbuild 로 번들해 실제 실행 (electron/supabase/db 는 스텁)

`scratchpad/pingtest/run.mjs`. 요청 횟수와 헤더를 직접 센다.

| 시나리오 | 요청수 | Authorization | restore | save |
|---|---|---|---|---|
| 메인 세션 있음 | 1 | O | 0 | 0 |
| **세션 없음 + 저장 토큰 (버그 상황)** | **1** | **O** | 1 | 1 |
| 저장 토큰도 없음 | 1 | X | 0 | 0 |
| 복원 실패 | 1 | X | 1 | 0 |
| 하트비트 | 1 | O | - | - |
| 첫 요청 실패 | 2 | O,O | - | - |

핵심은 **버그 상황에서도 요청이 1회**라는 것(중복 알림 없음).

## 워커 라벨은 진단용이지 수정이 아니다

`discord.ts` 의 `"(없음)"` → `"(토큰 없음 — 구버전/세션끊김)"`. 앱을 고친 뒤에도 이 문구가 보이면
그 사용자는 **구버전 앱**이라는 뜻이다(정보를 만들어내는 게 아니라 원인을 읽게 해 주는 것).
