# 디자인 갤러리 — 결정 사항

## 워커를 안 거친 이유
권한은 전부 Supabase RLS 와 SECURITY DEFINER 함수가 강제한다(읽기 공개, 쓰기 본인 것만,
관리자 함수는 JWT 이메일 검사). 중간에 워커를 하나 더 두면 인증 토큰을 넘기는 경로가
생기고 표면만 늘어난다. 앱이 인증된 Supabase 클라이언트로 직접 통신한다.

## 저장하는 것은 공유 코드 문자열뿐
설정 원본이 아니다. 공유 코드는 **그 오버레이 기본값에 있는 키만** 담으므로
API 키·룸 키가 구조적으로 들어갈 수 없다. 프리셋(AppSettings 전체 스냅샷)을 공유했다면
비밀값이 그대로 나갔을 것이다.

## 문자열 값 검증을 먼저 만든 이유
공개 업로드는 "모르는 사람이 만든 값을 내 화면에 넣는 것"이다. 색상·폰트 값이 CSS 커스텀
속성으로 들어가는데 커스텀 속성은 임의 토큰을 받고, var() 치환 때 선언이 하나 더 끼어든다.
  titleColor: "red; background-image: url(https://외부/추적.png)"
→ 남의 방송 화면이 모르는 서버로 요청을 보낸다. 갤러리를 열기 전에 막아야 했다.
규칙은 기본값 생김새에서 유도한다 — 키 목록을 따로 들면 오버레이가 늘 때 갱신을 잊는다.
HTML 주입은 원래 불가능함을 확인했다(renderText 가 textContent 만 쓴다).

## 신고 자동 숨김 + K 검토 (K 요청)
그냥 숨김만 풀면 누적 신고가 이미 임계값을 넘어 있어 **다음 신고 1건에 즉시 재숨김**된다.
`cleared_at` 을 둬서 K가 판단한 결과를 신고가 뒤집지 못하게 했다.
실측 확인: 신고 5회 → 숨김 / 확인 처리 → 공개 / 그 뒤 신고 8회 → 숨김 안 됨.
실제로 문제가 있으면 `preset_admin_hide` 로 직접 숨기고, 그때 확인 완료가 해제된다.

## 도배 방지는 DB 트리거로
앱에서만 검사하면 REST 를 직접 부르는 순간 뚫린다. 1인 30개 / 시간당 5개를 삽입 시점에
막고, (author_id, kind, name) 유니크로 같은 이름 반복도 막는다. 실측으로 중복 거부 확인.

## 썸네일을 안 받는 이유
카드마다 실제 오버레이 HTML 을 iframe 으로 띄우고 공유 코드를 postMessage 로 밀어 넣어
**실물 그대로** 보여 준다. 이미지 업로드는 저장 비용·검열 부담이 크고 실물과 어긋난다.
다만 목록을 열자마자 iframe 수십 개가 뜨면 안 되므로 IntersectionObserver 로
**화면에 들어온 카드만** 만든다.

## 관리자 판별
앱과 같은 이메일 기준이되 **DB 함수가 JWT 에서 읽는다**. 클라이언트가 보낸 등급을 믿으면
누구나 관리자가 된다. anon 역할에서는 관리자 함수 실행 권한을 명시적으로 회수했다 —
Supabase 가 public 스키마 함수에 기본 권한을 주므로 REVOKE FROM PUBLIC 만으로는 안 지워진다.

## 남은 것
- 실제 앱에서 화면 확인(카드 렌더·적용·업로드 왕복). 오버레이 서버(18181)가 떠 있어야 한다
- 지금은 최고 후원자 Type A 만 대상(`KIND = "a"`). 다른 오버레이는 KIND·기본값·파일명만 늘리면 된다

## 카드 미리보기에서 걸린 것 (실측)

**설정과 데이터를 같은 틱에 보내면 안 된다.** 설정 적용이 화면을 다시 그리면서 방금 넣은
후원자 데이터를 지운다. 한 틱 뒤에 보내야 남는다(기존 TopDonor 미리보기도 같은 이유로
지연을 둔다). 그리고 오버레이는 로드 직후 바로 못 받으므로 몇 번 더 보낸다.

**막다른 길 하나 기록**: 하네스에서 카드가 계속 비어 보여 헤더 차단·정규식·경로를 차례로
의심했는데 전부 아니었다. 원인은 **백그라운드 탭의 타이머 지연**이었다 — hidden 탭은
setTimeout 이 초 단위로 늘어져 push 가 늦게 나간다. 9초 기다리자 정상 렌더됐다.
앱은 화면에 떠 있으므로 해당 없다. 오버레이 미리보기를 하네스로 검증할 때는
이 지연을 감안해야 한다.

## 여러 종류로 확장 (K 요청: 애니메이션 타입 추가)

11종 전부 대상이 됐다(a·b·anim·c~j). 기본값은 `TopDonor.defaultsOf` 를 그대로 쓴다 —
기본값이 곧 공유 허용 목록이라 두 벌로 두면 값이 조용히 버려진다. 그래서 TopDonor 에서
`TabKind`·`TAB_KINDS`·`defaultsOf` 를 내보내 재사용한다.

**함정 두 개**:
- 오버레이 파일명이 종류명과 다르다. `anim` 은 `top-gift-ani.html` 이다.
  IPC 매핑(`TOP_DONOR_OVERLAY_KEY`)에는 `top-gift` 로 적혀 있는데 그 파일은 없다.
  실제 파일을 열어 보니 `top-gift` 와 `top-gift-ani` 를 **둘 다** 받으므로
  파일명에서 유도한 슬러그로 보내도 동작한다(실측 확인).
- `card` 는 탭에는 있지만 저장 가능한 종류가 아니다(`TOP_DONOR_TYPES` 에 없다). 목록에서 뺐다.

실측: 종류 선택 11개, anim 선택 시 `top-gift-ani.html` 로 렌더(왕관 포함),
적용이 `kind: "anim"` 으로 설정 53개를 전달한다.

## 적용 병합 순서 버그 (K 신고)

증상: 멀티 탑기프트 디자인을 적용한 뒤 기본 디자인을 적용해도 멀티가 안 꺼졌다.

원인은 공유 코드 설계와 병합 순서의 충돌이다. `encodeShareCode` 는 코드를 짧게 하려고
**기본값과 같은 값을 빼고** 담는다. 그래서 "멀티 끈 디자인"의 코드에는 `multiGift` 자체가
없다. 그런데 적용할 때 `{ ...defs, ...cur, ...values }` 순서라 현재 설정(켜짐)이 공유 값
뒤에 와서 그대로 살아남았다.

고침: 공유 대상 키(=기본값에 있는 키)는 **전부 그 디자인이 결정**한다.
  const shareable = { ...defs, ...values };   // 코드에 없으면 기본값으로 되돌림
  const next = { ...cur, ...shareable };      // 공유 대상 아닌 키만 현재 값 유지

실측 8건: 옛 방식으로 버그가 재현되고, 새 방식은 멀티가 꺼지며 개수도 기본값으로 돌아간다.
공유 대상이 아닌 키(룸 키 등)는 그대로 유지된다. 멀티↔기본 왕복도 정상.

## anim 색상 번짐 (K 신고)

증상: 닉네임 색만 바꿔도 타이틀·왕관 색까지 같이 변했다.

원인: `top-gift-ani.html` 에는 장식용 팔레트 3색(`--topgift-primary/secondary/accent`)이 있고
왕관·반짝임·선물 이미지·선물명 글로우가 **공유**한다. 그런데 코드가
  secondary ← usernameColor,  accent ← counterColor
로 채우고 있었다. 그 변수들은 닉네임·카운터와 아무 관계가 없다. 특히 타이틀의 인라인 필터
세 번째 그림자가 secondary 를 쓰므로 닉네임 색이 타이틀로 번졌다.

고침: 팔레트를 텍스트 색에서 떼어냈다. 텍스트 색은 `tdRenderText` 가 각 요소에만 칠한다.
`primary ← titleColor` 만 남겼다 — 전체 테마색 역할이고 팔레트를 바꿀 다른 UI가 없어
이것까지 끊으면 장식 색을 영영 못 바꾼다.

A/B 실측: 수정 전에는 닉네임 색 변경 시 타이틀 인라인 필터가 바뀌고, 수정 후에는
타이틀·선물명 글로우가 그대로다.

**따로 발견한 것(미수정)**: `applyVars(currentData)` 가 데이터 갱신 때마다 팔레트를
CONFIG 기본값으로 되돌린다(`currentData` 에는 primaryColor 가 없어 폴백이 걸린다).
그래서 CSS 변수 쪽 팔레트는 선물이 올 때마다 초기화된다. 타이틀·선물명은 인라인 필터를
쓰므로 눈에 안 띄지만, 왕관·반짝임은 영향을 받는다. 별도 건이라 이번엔 손대지 않았다.

## anim 추가 버그 2건 (같은 파일에서 전수조사 중 발견)

**1. 팔레트가 선물 올 때마다 초기화됐다.**
`applyVars` 하나가 배율과 팔레트를 같이 처리했고 데이터 갱신 경로에서도 불렸다. 그런데
`currentData` 는 `CONFIG` 를 물고 다니고 `CONFIG` 는 색을 **항상 기본값으로 채운다**
(`params.get('secondaryColor') || '#8b6cff'`). 그래서 선물이 하나 올 때마다 왕관·반짝임
색이 기본값으로 되돌아갔다. "값이 있을 때만 덮기"로는 안 막힌다 — 그 값이 늘 있기 때문이다.
`applyScale()` 과 `applyPalette()` 로 쪼개 **데이터 경로가 팔레트를 아예 못 건드리게** 했다.
팔레트 적용은 초기화 1곳만 남는다.

**2. 설정 반영 경로가 둘로 갈려 있었다.**
postMessage 핸들러와 WS 핸들러가 각각 설정을 처리했는데 **WS 쪽에만** 멀티 회전
시작/정지가 있었다. 그래서 미리보기(앱·갤러리·TTLS)에서 멀티를 꺼도 회전이 안 멈췄다.
`applySettingsMessage()` 하나로 합쳐 다시 갈라지지 않게 했다.

실측(수정 후): URL 로 지정한 팔레트가 선물 수신·설정 변경·재수신 내내 유지되고,
닉네임 색을 바꿔도 타이틀 글로우가 그대로이며, 멀티 on/off 가 postMessage 경로에서 동작한다.
콘솔 에러 0.
