# 오버레이 디자인 공유 — 결정과 이유

## 무엇을 가져오나
외부 대조 사이트 오버레이 갤러리의 **구조**만 가져온다. 남의 사용자 창작물(디자인 자체)은 가져오지 않는다.

핵심 메커니즘은 갤러리가 아니라 **공유 코드**다. 상세 페이지에 이렇게 적혀 있다 —
"복사한 코드를 앱의 오버레이 설정에서 붙여넣으면 이 디자인을 그대로 가져올 수 있습니다."
갤러리는 그 코드를 모아 보여주는 껍데기다. 코드가 되면 카톡으로도 공유되므로 갤러리 없이도 성립한다.

## 왜 기존 프리셋을 확장하지 않나

tikke 에는 이미 프리셋이 있다(`tikke:presets:save`). 하지만 그 저장 내용은 `snapshotSettings()` —
**AppSettings 전체**다. 거기엔 `tiktokSignApiKey`, `gtaGiftWebhooks`, 룸 키, TTS 키가 들어 있다.
프리셋을 그대로 공유 코드로 만들면 **사용자가 카톡에 자기 API 키를 붙여넣는 일**이 된다.

그래서 공유 코드는 스냅샷에서 빼는 방식(denylist)으로 만들지 않는다. 새 설정 키가 추가될 때
denylist 갱신을 잊으면 그날로 유출이다. **허용 목록으로만 구성한다** — 그 오버레이의 설정 객체에
있는 키만 담는다. 구조적으로 비밀이 닿을 수 없게 한다.

프리셋과 공유 코드는 목적이 다르므로 공존한다. 프리셋 = "내 전체 세팅", 공유 코드 = "오버레이 하나의 디자인".

## 왜 최고 후원자부터인가

두 가지가 맞물린다.
- 외부 대조 사이트 갤러리에서 가장 많이 공유되는 카테고리다(최고 후원자 Type A/B, 멀티 탑기프트).
- **tikke 쪽 구조가 이미 준비돼 있다.** `TopDonor.tsx` 는 오버레이 변종마다 독립된
  `DonorSettings` 객체 12개(a/b/anim/card/c~j)를 갖고 각자 기본값이 있다.
  EventOverlay 쪽 설정은 flat 네임스페이스라 "이 오버레이의 키가 무엇인가"부터 정해야 하지만,
  여기는 그 경계가 이미 그어져 있다.

또 선례도 있다 — `TopDonor.tsx` 의 "🎨 테마 프리셋"은 이미 **오버레이 단위 디자인 프리셋**이고,
`// 폰트는 프리셋이 건드리지 않음` 주석으로 "무엇이 디자인이고 무엇이 아닌가"의 경계를 이미 그었다.
그 옆에 다른 모양을 새로 만들지 않고 같은 결을 따른다.

## 가져오기는 기본값 위에 병합한다

붙여넣는 코드는 남이 만든 것이라 키가 빠져 있거나, 우리가 모르는 키가 있거나, 타입이 다를 수 있다.
그대로 넣으면 `undefined.toFixed()` 류로 렌더가 통째로 죽는다(과거 MvpUser 사고와 같은 부류).

그래서 가져오기는 이렇게 한다.
1. 코드 버전과 오버레이 종류가 맞는지 확인 — 다르면 거부(반쯤 적용하지 않는다)
2. 그 오버레이의 기본값에 **있는 키만** 통과
3. 타입 확인, 숫자는 범위 클램프
4. `{ ...기본값, ...통과한 값 }` 으로 적용

기존 로드 경로가 이미 `{ ...defaultsTypeA(), ...a.settings }` 라 같은 모양이다.

## 코드 형식

`TIKKE-1-<base64url(JSON)>` — JSON 은 `{ v, k, d }`.
- `v` 스키마 버전 — 나중에 형식이 바뀌면 옛 코드를 명확히 거부할 수 있다
- `k` 오버레이 종류(a/b/anim/…) — 다른 오버레이에 잘못 붙여넣는 것을 막는다
- `d` 설정 값
