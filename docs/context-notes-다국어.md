# 앱 다국어 (한국어 / 日本語 / English) — 결정과 이유

## 규모 (먼저 실측)
`apps/desktop/src` 기준 한글 문자열 리터럴 **약 4,955개**, 한글 포함 파일 **86개**.
페이지별 상위: EventOverlay 642 · WhatsNew 367 · TTSSettings 272 · TopDonor 260 · GiftBrowser 176.

한 번에 다 못 옮긴다. 인프라를 먼저 세우고 화면 단위로 옮긴다.
**옮기지 않은 화면은 한국어로 그대로 보인다** — 빈칸이나 키 이름이 뜨는 일은 없다(아래 참조).

## 핵심 결정: **한국어 원문이 곧 키다**

```ts
t("연결됨")          // ko: "연결됨"  ja: "接続済み"  en: "Connected"
```

사전에 없는 문자열은 **키(=한국어)를 그대로 돌려준다.**

왜 이렇게 하는가.
- **키를 새로 지을 필요가 없다.** 5천 개 문자열에 `settings.tts.title` 같은 이름을 붙이는 작업은
  번역 자체보다 오래 걸리고, 이름을 잘못 지으면 되돌리기 어렵다.
- **미번역이 곧 폴백이다.** 옮기다 만 화면도 한국어로 정상 동작한다. 배포 중간 상태가 안전하다.
- **마이그레이션이 기계적이다.** `"연결됨"` → `t("연결됨")` 로 감싸기만 하면 된다.
  키를 지어 붙이는 방식은 문자열마다 사람이 판단해야 해서 실수가 섞인다.

단점: 문맥이 다른데 한국어가 같은 문자열은 한 번역을 공유한다.
(예: "이름"이 여러 화면에 있음) 실제로 문제가 되면 그때 `t("이름", { ctx: "선물" })` 로
문맥 접미사를 붙인다. 지금 미리 만들지 않는다 — 아직 실제 충돌 사례가 없다.

## 구조
- `src/i18n/index.ts` — `Lang` 타입, `t()`, zustand 스토어(`useLangStore`)
- `src/i18n/ja.ts` / `src/i18n/en.ts` — `Record<한국어, 번역문>`
- 저장: 설정 키 `appLanguage`. 앱 시작 시 읽어 스토어에 넣는다
- 선택 UI: 상단바(StatusBar) — K 요청 "상단에서 언어 선택"

## 렌더링 갱신
`t()` 가 순수 함수라 언어를 바꿔도 리렌더가 안 걸린다. 그래서 컴포넌트는
`useLang()` 을 구독하고, 그 값이 바뀌면 React 가 다시 그린다.
전역 리마운트(key 갱신)로 처리하면 페이지 상태(스크롤·입력값)가 날아가므로 쓰지 않는다.

## 옮기는 순서 (눈에 띄는 것부터)
1. 사이드바 메뉴 · 상단바 — 앱 인상을 좌우한다
2. 대시보드 · 연결 — 첫 화면
3. TTS · 이벤트 오버레이 · 최고 후원자 — 사용 빈도 최상위
4. 나머지

## 안 하는 것
- 외부 라이브러리(i18next 등) 도입: 의존성 대비 얻는 게 없다. 필요한 건 사전 조회 하나뿐이다.
- 오버레이 HTML 번역: 오버레이는 시청자에게 보이는 화면이라 방송인 UI 언어와 무관하다.
  필요해지면 별건으로 다룬다.
- 자동 번역 API 연동: 런타임 비용·지연·오역 위험. 사전은 정적 파일로 둔다.
