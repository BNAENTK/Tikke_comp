## 🔴 높음

### 1. TTS 정지 버튼이 큐를 비우지 못함 — `src/hooks/useTTSEngine.ts:887`

`stopAudioRef`는 `useRef<(() => void) | null>`(370행)인데, Web Speech 경로에서 타입을 강제로 바꿔 넘긴다.

```ts
speakWebSpeech(text, {...}, stopAudioRef as unknown as { current: SpeechSynthesisUtterance | null }, ...)
```

`speakWebSpeech`는 796행에서 `utteranceRef.current = utterance`를 하므로, 결과적으로 `stopAudioRef.current`에 **함수 대신 `SpeechSynthesisUtterance` 객체**가 들어간다.

정지 핸들러(736행)는 이걸 함수로 호출한다.

```ts
if (stopAudioRef.current) { stopAudioRef.current(); stopAudioRef.current = null; }
```

→ `TypeError: stopAudioRef.current is not a function`. 예외가 핸들러 중간에서 터지므로 **그 아래 정지 로직이 전부 실행되지 않는다**. `mvpStopAudioRef` 정지, `isSpeakingRef` 해제, `state.clearQueue()`, `setSpeaking(false)` 모두 건너뛴다.

재현: TTS 프로바이더를 `google_female` 또는 `webspeech:*`로 설정 → 읽는 중 정지 → 현재 발화는 `speechSynthesis.cancel()`로 멈추지만 대기열이 남아 다음 항목부터 계속 읽는다.

같은 파일 443행은 같은 함수에 `utteranceRef`를 제대로 넘기고 있다. 887행만 어긋나 있어 실수로 보인다.

### 2. 리그 배지 조회가 빈 결과를 반환할 수 있음 — `electron/main/ipc.ts:1665-1667`

```ts
const leagueRows = await Promise.any([
  uid ? browserFetch(`...user_league_data?unique_id=eq.${uid}...`) : Promise.resolve([]),
  did ? browserFetch(`...user_league_data?unique_id=eq.${did}...`) : Promise.resolve([]),
]).catch(() => []);
```

문제 두 개가 겹쳐 있다.

**(a) `Promise.any`가 빈 배열을 먼저 집는다.** `Promise.any`는 처음 *이행된* 프로미스로 확정된다. `uid`가 빈 문자열이면 첫 항목이 `Promise.resolve([])`라 **즉시** 이행되고, 아직 진행 중인 `did` 쿼리 결과는 버려진다. 즉 displayId만 넘기면 리그 데이터가 항상 빈 값이다. 반대도 같다. 둘 다 있어도 HTTP 응답 순서에 따라 빈 쪽이 이길 수 있다(`r.ok`가 false여도 `[]`로 이행됨).

**(b) 두 쿼리가 같은 컬럼을 본다.** `did`(display_id)도 `unique_id=eq.`로 조회한다. 바로 아래 1676-1680행의 순위 조회는 `broadcaster_unique_id`와 `display_id`를 제대로 구분하고 있어 대비된다.

영향: 연결된 앵커 리그 배지(anchor-badge)의 티어/점수가 비어 보임.

### 3. AI 코호스트가 실패 시 쿨다운 없이 API를 계속 호출 — `electron/services/cohost-ai.ts:174-179`

```ts
const output = await callLLM(cfg, prompt);
if (!output) {
  lastResponse = { ...error: "응답 없음 (API 키/네트워크 확인)" };
  return;                    // <- lastResponseAt 갱신 없이 빠져나감
}
lastResponse = { input: prompt, output, ts: now };
lastResponseAt = now;
```

`lastResponseAt`은 성공했을 때만 갱신된다. 169행의 쿨다운 게이트가 `now - lastResponseAt < cfg.minChatGapSec * 1000`이므로, API 키가 틀렸거나 네트워크가 끊겨 `callLLM`이 계속 null을 반환하면 **쿨다운이 영원히 열려 있다**. `triggerMode: "auto"`에서 채팅 한 줄마다 LLM 요청이 나간다. `busy` 플래그가 동시 실행만 막을 뿐 빈도는 못 막는다.

영향: 유료 API 쿼터 소진, 레이트 리밋. 하필 이미 실패 중일 때 가장 심하게 호출한다.

## 🟡 중간

### 4. `connect()`에 재진입 가드가 없어 리스너가 중복될 수 있음 — `electron/services/tiklive.ts:315-318`

```ts
async connect(username: string, sessionId?: string): Promise<void> {
  if (this.connection) {
    await this.disconnect();
  }
```

진행 중 상태를 나타내는 플래그가 없다. `live-monitor`의 자동 연결과 사용자의 수동 연결이 겹치면 두 호출 모두 `this.connection`이 아직 null인 시점을 통과할 수 있다. 그러면 `attachListeners`가 같은 커넥션 객체에 두 번 붙어 **모든 이벤트가 두 번 처리된다** — TTS가 채팅을 두 번 읽고, 선물 사운드가 두 번 울리고, 오버레이 이벤트가 중복된다.

좁은 창이지만 자동 연결이 10초 주기로 도는 구조라 실제로 겹칠 수 있다.

### 5. Qwen TTS 파이썬 프로세스가 좀비로 남을 수 있음 — `electron/services/qwen-tts-manager.ts:146-158, 161-168`

exit 핸들러가 모듈 전역 `_proc`를 **조건 없이** 지운다.

```ts
_proc.on("exit", (code) => { _proc = null; _ready = false; _starting = false; });
```

`stopQwenTTSServer()`는 kill 직후 `_proc = null`로 만들고 exit를 기다리지 않는다(161-168행). 그래서 정지 → 재시작을 빠르게 하면, 새 프로세스 B가 `_proc`에 들어간 뒤에 옛 프로세스 A의 exit가 도착해 **B의 핸들을 지운다**. 이후 앱 종료 시 `stopQwenTTSServer()`의 `if (_proc)`가 false라 kill을 건너뛰고, 파이썬 서버가 포트 18186을 잡은 채 남는다. 그 상태에서 다시 시작하면 `_proc`가 null이라 세 번째 프로세스까지 뜬다.

같은 함수의 부수 문제: `stopQwenTTSServer()`가 `_starting`을 리셋하지 않는다. 워밍업 중(`Application startup complete` 출력 전) 정지하면 `_starting`이 true로 남아 다음 `startQwenTTSServer()`가 104행 가드에서 조용히 반환한다. A의 exit가 도착하면 `_starting`이 풀리지만 그때는 아무도 재시작을 시도하지 않아 서버가 내려간 채 방치된다.

고치려면 핸들러를 등록할 때 프로세스를 지역 변수로 잡고 `if (_proc === proc)`로 가드하면 된다.

### 6. CRM 집계가 네트워크 실패 시 유실됨 — `electron/services/crm-collector.ts:143-145`

```ts
const batch = Array.from(pendingDeltas.values());
pendingDeltas.clear();          // <- 업서트 전에 비움

for (const d of batch) {
  try { ... await sbFetch("/rest/v1/viewer_crm", {...}) ... }
  catch (err) { console.error("[crm-collector] flush error:", err); }
```

델타를 큐에서 먼저 비우고 업서트를 시도한다. 실패는 로그만 남기고 **재큐잉하지 않는다**. 방송 중 네트워크가 잠깐 끊기면 그 3초 배치의 다이아/방문/선물 증분이 영구히 사라진다. 누적 통계라 이후 값이 계속 낮게 유지된다.

### 7. ffmpeg 설치 실패 시 임시 파일이 남음 — `electron/services/ytmp3-service.ts:100-109`

```ts
await extractZip(zipPath, tmpDir);
for (const exe of ["ffmpeg.exe", "ffprobe.exe"]) {
  const found = findFile(tmpDir, exe);
  if (!found) throw new Error("구성요소 압축 해제 실패");
  copyFileSync(found, join(binDir(), exe));
}
rmSync(zipPath, { force: true });
rmSync(tmpDir, { recursive: true, force: true });
```

`extractZip`이 던지거나 `findFile`이 null이면 두 `rmSync`를 건너뛰고 117행 catch로 간다. 약 90MB zip과 압축 해제된 트리가 그대로 남는다. 재시도할 때마다 그 위에 다시 90MB를 받는다. `finally`로 옮기면 된다.

## 부수적으로 확인한 정상 사항

- **오버레이 desktop ↔ worker 동기화 완전**. `apps/desktop/public/overlays` 57개 중 `index.html`을 뺀 56개가 `apps/worker/public/overlay`에 전부 있고 **바이트 단위로 동일**하다. 스킬이 "가장 잦은 함정"으로 지목한 항목인데 현재는 깨끗하다.
- `live-monitor.ts` 백오프 분류, `auto-like.ts` 타이머 정리는 감사에서 문제 없음으로 나왔다.
- `playBufferSafe`(useTTSEngine)의 `void audioCtx.resume()` 미대기는 워치독과 함께 설계된 방어 코드로, 의도된 패턴이다.
