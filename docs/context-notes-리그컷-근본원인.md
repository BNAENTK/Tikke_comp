# 리그 조각컷이 계속 틀리는 근본 원인 (2026-08-06)

## 한 줄
**앵커마다 오차가 있는 추정값들의 "최댓값"을 취한다. 최댓값은 참값이 아니라 가장 크게 틀린
관측으로 수렴한다.** 그리고 DB 트리거가 그걸 되돌릴 수 없게 못박는다.

## 어디서 일어나나 — 두 겹으로 적용된다

**1) DB 트리거 (되돌릴 수 없음)**
```sql
CREATE FUNCTION league_cutoffs_monotonic() RETURNS trigger AS $$
BEGIN
  IF NEW.cutoff_score < OLD.cutoff_score THEN
    NEW.cutoff_score := OLD.cutoff_score;   -- 새 값을 버리고 옛 값 유지
  END IF;
  RETURN NEW;
END $$
```
`cutoff_score` 만 옛 값으로 되돌리고 `owner_score`/`gap_amount`/`anchor_rank`/`snapshot_at` 은
새 값으로 갱신된다 → **한 행 안에 서로 다른 시점의 관측이 섞인다.**
`cutoffs.ts:246` 의 "저장된 cutoff_score 가 다른 시점 값으로 덮여 어긋난 행이 있다" 가 이것이다.
원인을 모른 채 증상만 우회하고 있었다.

**2) serve 측 MAX** — `cutoffs.ts` "퍼센타일별 MAX cutoff_score 채택".
같은 상방 편향이 한 번 더 걸린다.

## 왜 MAX 가 틀렸나
"컷은 하루 중 상승만 한다" 는 **맞다**. 그래서 낮은 값은 낡은 값처럼 보인다.
하지만 그 논리는 *같은 추정기의 시간에 따른 변화*에만 성립한다.
우리 관측은 **매번 다른 앵커**에서 나오고 앵커마다 오차가 다르다.
서로 다른 추정기들 사이에서 MAX 를 취하면 참값이 아니라 **오차의 최댓값**을 뽑는다.
하루가 갈수록 위로 벌어지고, 래칫이라 내려올 수 없다.

## 증거

**(a) 외부 자료 없이 자체 모순으로 증명된다.**
컷이 오르기만 한다면 **가장 최근 관측이 항상 최대**여야 한다.
그런데 오늘 55개 셀 중 **32개에서 `cutoff_score` > `owner_score+gap_amount`(최신 관측)** 이다.
성장으로는 설명되지 않는다 — 저장값이 부풀려진 관측을 물고 있다는 뜻이다.
1.5배 초과 6개, 2배 초과 3개, 최악 3.18배.

**(b) 정답지 대조(외부 대조 사이트).** 비교 가능한 54개 셀에서
래칫이 정답에 더 가까운 셀 **2개**, 최신 원자료가 더 가까운 셀 **25개**, 동일 27개.
**해친 25개 전부 저장값이 정답보다 크다** — 편향이 한 방향이다.
(외부 대조 사이트 스냅샷이 몇 시간 전이라 정답은 하한이다. 그래도 방향과 (a)의 자체 모순은 그대로다.)

극단 사례:
| 리그 | % | 저장(서빙) | 최신 관측 | 외부 대조 사이트 |
|---|---|---|---|---|
| B4 | 1 | **315,685** | 99,137 | 99,137 |
| A2 | 60 | 15,603 | 8,823 | 3,977 |
| B3 | 70 | 6,211 | 3,048 | 1,750 |
| A2 | 20 | 91,825 | 34,459 | 26,238 |

B4 1% 의 최신 관측 99,137 은 **외부 대조 사이트와 소수점까지 일치**한다. 참값은 이미 우리 손에 있는데
래칫이 3.2배 부풀린 옛 값을 계속 내보내고 있었다.

## 이게 설명하는 것들 (이번 세션 내내 쫓던 증상 전부)
- **"신선한데 틀린 값"** — `snapshot_at` 은 매 주기 갱신되니 신선해 보이는데
  `cutoff_score` 는 과거 최댓값에 얼어붙어 있다. 신선도 검사로는 절대 안 잡힌다.
- **빈칸** — serve 가드가 부풀려진 값을 이상치로 걸러낸 것이다. **가드는 제대로 일하고 있었다.**
  "가드가 과잉 차단한다"는 내 가정이 틀렸다. 원인은 가드가 아니라 입력값이었다.
- **퍼센타일 겨냥·회전 작업이 체감 개선을 못 준 이유** — 원자료 정확도는 올렸지만
  서빙되는 값은 래칫에 걸린 옛 최댓값이라 바뀌지 않았다.
- **하루가 갈수록 오차가 커지는 패턴** — 관측이 쌓일수록 최댓값이 위로만 간다.

## 왜 스스로 못 고치나 — 관측 이력이 없다
UNIQUE 키가 `(class_type, percentile, league_tier_id, league_date, source)` 라
**셀당 하루 1행**이다. 관측을 여러 개 보관하지 않으니
- 중앙값·이상치 제거 같은 견고한 통계를 쓸 수 없고
- 잘못된 값이 들어와도 되돌릴 원본이 없다
→ 그래서 "MAX 채택"을 트리거로 흉내 냈고, 그게 일방통행 함정이 됐다.

(과거 285만 행 폭증 사고 때문에 이 제약을 넣은 것인데, 그때 문제는 제약이 **아예 없어서**였다.
지금은 7일 보존 정리가 있으므로 셀당 관측을 여러 개 두어도 상한이 있다:
55셀 × 30분 크론 48회 ≈ 2,600행/일, 7일 ≈ 18,000행. 폭증 때와 두 자릿수 차이다.)

## 고치는 방향 (아직 미적용 — K 판단 대기)
1. **트리거 제거 또는 조건부화.** 지금은 무조건 최댓값 유지 = 되돌릴 수 없음.
2. **관측 이력 보관.** UNIQUE 키에 관측 시각을 넣어 셀당 여러 행을 남긴다.
3. **MAX 대신 견고한 통계.** 이력이 생기면 최신 관측 우선 + 명백한 이상치만 제외.
   최댓값은 노이즈를 뽑는다.
4. 되돌릴 때 **값이 내려간다** — 지금 서빙 중인 값이 부풀려져 있으므로 정상이다.
   K 에게 미리 알리고 진행할 것.

주의: 트리거만 떼면 이번엔 "낡은 저품질 앵커의 낮은 값"이 그대로 나갈 수 있다.
1→2→3 을 같이 해야 한다. 하나만 하면 반대쪽으로 틀린다.
