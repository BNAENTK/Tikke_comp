# 번역 확정 속도 — 결정 노트 (A안: 체감 변화 없는 것만)

## 요구 (K)
길게 말할수록 번역 확정이 느려진다. 단, **기존 체감과 달라지면 안 된다** —
"더 좋아졌다"만 느껴야 하고 "뭔가 이상한데"는 절대 안 됨.

## 후보 3개 중 2개는 기각
- **문장 단위로 끊어 확정(B안)** — 효과는 제일 크지만 화면에 나오는 게 달라진다.
  한 줄이던 게 여러 카드로 쪼개지고, 줄 쌓기 1줄 설정이면 앞 문장이 바로 밀려 사라진다.
  → K 제약에 정면으로 걸림. 보류, K가 눈으로 보고 결정.
- **꼬리만 번역해서 이어붙이기** — `번역(A+B) ≠ 번역(A)+번역(B)`.
  한국어는 어순이 뒤라 이어붙이면 번역문이 눈에 띄게 어색해진다. 속도 얻고 품질 잃음. 기각.

## 진짜 원인 (코드에서 확인)
`_gtxRaw` 의 429 쿨다운 분기가 **의도와 반대로 동작**하고 있었다.
```js
if (now < _gtxCooldownUntil) {
  if (isInterim) return '';
  return _myMemory(text, tl);   // ← final 을 폴백 번역기로 보냄
}
```
주석은 "interim 폭주가 final 까지 굶기는 것 방지"인데, 실제로는 굶기는 쪽이었다.

흐름: 길게 말함 → interim 이 250ms마다 **누적 원문 전체**를 언어 수만큼 재번역 →
요청이 몰려 429 → 쿨다운 3초 → 그 사이 도착한 **확정 번역이 gtx 를 건너뛰고 MyMemory 로 감**.
MyMemory 는 더 느리고(측정 모델 900ms+) 번역 품질도 다르다.
그래서 길수록 느려지고, interim 에 떠 있던 번역과 확정 자막의 문장이 **다르게** 바뀌기까지 했다.

## 적용 (전부 화면 출력이 안 바뀌는 것만)
1. **쿨다운 중에도 final 은 gtx 를 시도한다.** final 은 언어당 1건뿐이라 흐름을 안 막는다.
   그마저 429 면 기존 catch 가 MyMemory 로 넘긴다 — 폴백은 그대로 살아 있다.
2. **번역 캐시** `(원어, 대상언어, 원문) → 번역문`, 300개 상한.
   같은 문장을 두 번 번역하지 않는다.
3. **동시요청 합치기(상한 있음).** 같은 요청이 아직 응답 대기 중이면 그 응답에 합류 —
   final 이 마지막 interim 요청에 올라타면 왕복 한 번을 통째로 아낀다.
   합류한 결과가 빈 값이면 final 은 자기 경로(폴백 포함)로 다시 시도한다.

   **여기서 한 번 잘못 고쳤다가 되돌렸다.** "final 은 interim 이 띄운 요청에 합류하지 않는다"로
   막아 봤더니(느린 요청에 묶이는 걸 피하려고) 오히려 나빠졌다 — final 이 매번 자기 요청을
   새로 던져 레이트리밋을 맞고 다시 폴백으로 샜다. 측정치: 429 0→2, 폴백 0→2.
   정답은 **합류하되 상한**(`JOIN_MAX_MS = 1500`). 상한 안에 오면 왕복 하나를 통째로 아끼고,
   늦으면 그때 자기 길로 간다. 손해는 최대 1.5초로 묶인다.

캐시 키에 원어를 넣는다 — 원어가 바뀌면 같은 문장도 번역이 달라지기 때문.

## 측정 (실제 gtx 대신 지연·429 모사 목으로 재현, base=개선 전 / new=개선 후)
| 시나리오 | | 확정까지 | gtx 요청 | 429 | 폴백 | 말하는 중 번역칸 갱신 |
|---|---|---|---|---|---|---|
| 긴 발화 | base | 1559ms | 12 | 2 | 2 | 4회 |
| 긴 발화 | **new** | **671ms** | 10 | **0** | **0** | 4회 |
| 짧은 발화 | base | 624ms | 4 | 0 | 0 | 1회 |
| 짧은 발화 | **new** | 629ms | 4 | 0 | 0 | 1회 |

짧은 발화는 **확정 자막이 글자까지 동일**하고 시간도 그대로다(이미 왕복 1회 = 하한).
개선이 붙는 지점은 요청이 몰려 429 가 나는 긴 발화뿐 = K 제약과 정확히 일치한다.

**말하는 중 번역칸 갱신 횟수를 같이 잰 이유**: 1번 변경으로 final 도 쿨다운 중에 gtx 를
때리게 됐는데, 그게 429 를 맞으면 쿨다운이 3초 더 밀려 **진행 중 번역칸이 더 오래 얼어붙을**
수 있다. 확정만 빨라지고 말하는 중이 얼면 K 제약 위반이다. 실측 4회 → 4회로 동일해서 남겨 뒀다
(new 는 애초에 429 를 안 맞아서 쿨다운이 안 걸린다). 이 수치는 앞으로도 같이 봐야 한다.

정직하게: 이번 이득은 대부분 1번(쿨다운)에서 나왔다. 2·3번은 이 시나리오에선 요청 2건을
줄였을 뿐이다. 다만 실제 방송은 같은 말을 반복하고 요청 타이밍이 겹치는 일이 잦아
거기서 더 붙는다.

## "말 끝 → 확정 텀" 조사 (2026-08-06) — 선번역은 넣었다 뺐다

K: "말이 끝나고 자막 확정까지 텀이 너무 길다."

텀은 두 덩어리다.
1. **Chrome 이 "발화 끝났다"고 판정하는 시간** — Web Speech API 에 설정이 없다. 우리가 못 바꾼다.
2. **확정을 받고 자막을 완성하기까지 (우리 몫)**

2번을 실제 Google 번역기로 쟀다. 1번을 gap 으로 흉내 내며 변화시켰다(번역 2개, 문장 3개 평균).

| gap | 확정 도착 → 화면 첫 변화 | 확정 도착 → 완성 |
|---|---|---|
| 200ms | 99~700ms | 388~987ms |
| 500ms | **2ms** | 293ms |
| 900ms | **2ms** | 291ms |
| 1500ms | **2ms** | 290ms |

**gap 이 500ms 만 넘으면 우리 몫은 사실상 0이다**(첫 변화 2ms). 남는 291ms 는 전부
승격 카드 등장 애니메이션(`gsap.from opacity 0, duration 0.25 + stagger`)이다.
이미 돌고 있는 250ms interim 스로틀이 마지막 원문을 번역해 캐시에 넣어 두기 때문이다.

그래서 "말이 멈추면 미리 번역해 두는" 선번역(`PREWARM_MS`)을 **실제로 구현해서 재봤고, 폐기했다.**
- gap ≥ 500ms: 이득 0 (base 가 이미 하한). 오히려 486ms·2407ms 같은 이상치가 생겼다.
- gap 200ms: 개선 없음. 선번역 타이머가 발화 도중에도 걸려 요청이 늘고, 그게 레이트리밋을 불렀다.

**다시 시도하지 말 것.** 250ms 스로틀이 이미 선번역 역할을 하고 있다.

남은 우리 쪽 레버는 등장 애니메이션 291ms 하나뿐이고, 그건 속도가 아니라 연출 선택이다.
나머지는 전부 Chrome 몫이라 `stop()` 강제 확정 말고는 방법이 없는데, 그건 말하다 쉰 것을
끝으로 오해해 **문장을 자른다** — K 가 이미 겪는 "짧아짐"과 같은 계열이라 안 한다.

## 남은 것
"길게 말하면 확정 자체가 안 뜨고 계속 늘어남"은 **안 없어졌다**.
Chrome 이 말이 끊길 때까지 확정을 안 주는 구조라 B안(문장 끊기) 없이는 근본 해결이 안 된다.
