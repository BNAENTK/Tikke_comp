# Tikke 유튜브 버전 — 가능성 조사 + 설계 (2026-08-13)

범위: **설계까지만.** 코드 없음.

## 결론

**가능하다.** 그리고 생각보다 싸다 — 앱의 거의 전부를 그대로 쓴다.

이유는 지금 구조가 이미 갈라져 있기 때문이다. 이벤트 **생산자는 `tiklive.ts` 하나**뿐이고,
그 뒤는 전부 `TikkeEvent` 라는 공용 타입만 본다.

```
tiklive.ts(909줄)  →  normalizeEvent  →  eventQueue  →  eventBus  →  소비자 20+
                                                                    (오버레이/TTS/게임/
                                                                     사운드룰/CRM/덱/GTA…)
```

소비자 중 어느 것도 틱톡 SDK 를 직접 부르지 않는다. 즉 **생산자만 갈아끼우면 된다.**

- 새로 써야 하는 것: 유튜브 어댑터 1개(= `tiklive.ts` 자리) + 연결 화면 + 기능 게이팅
- 그대로 쓰는 것: 오버레이 전부, TTS, 사운드 룰, 게임 5종, 명령어, 코호스트 AI,
  단골 카드(CRM), 덱, 클라우드 오버레이, 이벤트 로그

## 1. 수집 경로 — 두 갈래

### A안. 공식 YouTube Data API v3

- `liveChatMessages.list` — 폴링. 응답이 `pollingIntervalMillis` 로 다음 호출 시점을 지시한다.
- `liveChatMessages.streamList` — **서버 스트리밍**. 문서가 "폴링 필요를 줄여 쿼터 초과를 피한다"고
  명시적으로 권한다. 끊기면 `nextPageToken` 으로 이어받는다.
- 인증: OAuth (방송인 본인). Tikke 는 본인이 쓰는 앱이라 이 모델이 맞는다.

**미확인**: `liveChatMessages.list` / `streamList` 의 정확한 쿼터 단가가 공식 쿼터 표에 **없다**.
기본 한도는 하루 10,000 units. 단가가 1이라고 가정하면 폴링(1~5초)으로 하루 3~14시간이 한계라
장시간 방송에 빠듯하다. **streamList 가 이 문제를 푸는 열쇠인데 그 단가를 확인해야 한다.**
쿼터 증액은 Google 심사 신청이 필요하다.

### B안. 비공식 InnerTube — `LuanRT/YouTube.js`

- **5,096⭐, 마지막 커밋 2026-08-13(어제).** MIT. 살아 있는 유일한 후보.
- 대안들은 사실상 방치: `LinaTsukusu/youtube-chat`(247⭐, 2023-06),
  `sigvt/masterchat`(87⭐, 2024-05).
- 로그인·쿼터 없음. 시청자 누구나 보는 채팅을 그대로 읽는다.
- **소스에서 확인한 파싱 클래스** (`src/parser/classes/livechat/items/`):

| 클래스 | 무엇 |
|---|---|
| `LiveChatTextMessage` | 일반 채팅 |
| `LiveChatPaidMessage` | **슈퍼챗** (`purchase_amount`, 색상 티어) |
| `LiveChatPaidSticker` | **슈퍼스티커** |
| `LiveChatMembershipItem` | **멤버십 가입/갱신** |
| `LiveChatSponsorshipsGiftPurchaseAnnouncement` | **멤버십 선물(기프팅)** |
| `LiveChatSponsorshipsGiftRedemptionAnnouncement` | 선물 수령 |
| `CreatorHeartView` | 크리에이터 하트 |
| `LiveChatBannerPoll` | 투표 |
| `UpdateViewershipAction` | **시청자 수** |

- 이벤트: `start` / `chat-update` / `metadata-update` / `error` / `end`.
  구조가 지금 `tiklive.ts` 의 `conn.on(eventType, ...)` 와 거의 1:1 이다.

### 권고

**B안(YouTube.js)으로 만들고, A안을 나중에 선택지로 남긴다.**

- 틱톡판이 이미 비공식 경로(`tiktok-live-connector`)라 운영 감각이 같다
- 쿼터가 없어 장시간 방송에 안전하고, 사용자가 구글 로그인/API 키를 안 만들어도 된다
- 대신 **유튜브가 내부 응답을 바꾸면 깨진다**. 라이브러리가 활발한 게 그래서 중요하다
- ToS: 비공식 내부 API 이용이라 회색지대다. 틱톡판과 같은 성격의 위험을 하나 더 지는 것 —
  **K 가 판단할 사업 결정이지 기술 결정이 아니다.**

## 2. 이벤트 매핑

| Tikke 이벤트 | 틱톡 | 유튜브 | 비고 |
|---|---|---|---|
| `chat` | 채팅 | `LiveChatTextMessage` | 그대로 |
| `gift` | 선물(다이아) | **슈퍼챗 / 슈퍼스티커** | 아래 "돈 단위" 참고 |
| `member` | 입장 | — | **없음.** 유튜브는 입장 이벤트가 없다 |
| `subscribe` | 구독 | `LiveChatMembershipItem` | 멤버십 가입 |
| `follow` | 팔로우 | — | 없음(구독 알림은 실시간 채팅에 안 옴) |
| `like` | 좋아요 | `metadata-update` 의 좋아요 수 | 개별 이벤트 아님 — **총계만**, 증분으로 환산 |
| `share` | 공유 | — | 없음 |
| `roomUser` | 시청자 수 | `UpdateViewershipAction` | 그대로 |
| `emote` | 이모트 | 채팅 내 이모지 | 별도 이벤트 아님 |
| `envelope` | 봉투 | — | 없음 |
| `linkMicBattle/Armies` | PK 배틀 | — | **없음.** 유튜브에 대응 개념 없음 |
| `streamEnd` | 종료 | `end` | 그대로 |

### 돈 단위 — 설계에서 제일 조심할 곳

틱톡은 `diamondCount`(정수, 전 세계 동일). 유튜브 슈퍼챗은 **`purchase_amount` 가 문자열**이고
**통화가 시청자마다 다르다**(`₩5,000`, `$2.00`, `¥500`).

- 소비자(탑기프트·사운드 룰·게임 티켓·CRM)는 전부 **정수 비교**를 한다 → 정규화가 필수
- 제안: `diamondCount` 자리에 **원화 정수**를 넣고, 원문 통화·금액은 `raw` 에 보존
- 환율은 앱 시작 시 1회 받아 캐시(하루 1회 갱신). 실패하면 마지막 값 사용
- ⚠ **콤마 파싱 함정**: `parseInt("5,000")` → `5`. 이 코드베이스에서 이미 한 번 크게 터진 적 있다
  (리그 컷 gap 전면 오염, 2026-07-13). **`.replace(/[^\d.]/g,"")` 후 파싱**을 규약으로 못 박을 것
- 티어 색상(`header_background_color`)은 유튜브 슈퍼챗 등급이라 오버레이 연출에 그대로 쓸 수 있다

### 선물 이미지가 없다

틱톡판 오버레이는 선물 이미지를 그린다(장미·고래 다이빙…). 유튜브 슈퍼챗엔 이미지가 없고
**금액 색상 티어**만 있다. 슈퍼스티커는 이미지가 있다.

→ 오버레이는 "선물 이미지 없으면 금액 티어 배지로 그리기" 폴백이 필요하다.
탑기프트는 금액 기준이라 그대로 동작한다(방금 선물 기준 정렬로 바꿔둔 게 여기서도 맞는다).

## 4. 구현 계획

### 형태 — 별도 앱이 아니라 **한 앱 안의 모드**

`apps/desktop` 을 복제하지 않는다. 복제하면 오버레이 59개와 서비스 수십 개가 두 벌이 되어
지금까지 겪은 "desktop↔worker 사본 불일치" 문제가 통째로 재현된다.

`platform: "tiktok" | "youtube"` 설정 하나로 갈라지게 한다.

### 단계

1. **경계 정리** — `tiklive.ts` 에서 이벤트 생산 부분과 틱톡 전용 부분을 분리.
   `LiveSource` 인터페이스 정의: `connect(id)` / `disconnect()` / `getUsername()` / 이벤트 방출.
   → 이 단계는 틱톡판만으로도 이득(테스트 가능해짐).
2. **유튜브 어댑터** — `services/youtube-live.ts`. YouTube.js 의 `chat-update` 를
   `normalizeEvent` 가 먹을 모양으로 변환. 금액 정규화 포함.
3. **연결 UI** — 지금 "TikTok 사용자 이름" 자리에 채널 URL/핸들/영상 ID 입력.
   라이브 영상 ID 해석은 YouTube.js 가 해준다.
4. **기능 게이팅** — 사이드바·설정에서 플랫폼별로 항목을 숨긴다.
   지금 `locked: true` / `import.meta.env.DEV` 게이트와 같은 방식.
5. **오버레이 폴백** — 선물 이미지 없을 때 금액 티어 배지.
6. **접속 알림/과금** — 워커 `/ping` 에 `platform` 필드 추가(디스코드 알림 구분).

### 규모 추정

| 단계 | 크기 |
|---|---|
| 1. 경계 정리 | 중 — 기존 코드를 옮기는 일이라 위험은 낮고 양이 있다 |
| 2. 유튜브 어댑터 | 중 — 새 코드 400~600줄 예상 |
| 3. 연결 UI | 소 |
| 4. 게이팅 | 소 — 다만 **빠뜨리기 쉬움**. 목록을 만들어 기계 검사 걸 것 |
| 5. 오버레이 폴백 | 소~중 — 오버레이 개수만큼 확인 필요 |
| 6. 알림/과금 | 소 |

## 5. 위험과 미확인

**미확인 — 진행 전에 확인해야 할 것**
- `liveChatMessages.streamList` 의 쿼터 단가(공식 표에 없음). A안을 쓸지 말지가 여기서 갈린다
- YouTube.js 로 **실제 한국 라이브 방송**에 붙여 슈퍼챗/멤버십이 기대대로 오는지 실측
  (지금까지는 소스 코드로 클래스 존재만 확인했다. 실측 아님)
- 유튜브 슈퍼챗의 통화 표기 실제 형태(원문 문자열 샘플)

**위험**
- 비공식 경로는 유튜브가 바꾸면 깨진다. 라이브러리 갱신 속도에 묶인다
- ToS 회색지대 — 사업 판단 필요
- 게이팅 누락 시 유튜브 사용자에게 리그 화면이 보인다(빈 화면 = 버그로 보임)
- 금액 정규화가 틀리면 탑기프트·사운드 룰·게임이 전부 조용히 어긋난다.
  **여기에 테스트를 먼저 깔 것**

**안 해도 되는 것**
- 앱 복제 금지. 오버레이·워커 사본이 두 벌 되는 순간 유지가 무너진다
