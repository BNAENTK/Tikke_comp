# context-notes — 선물 브라우저 실시간 수집 + 최신순 정렬

## 2026-07-27

### "최신순"을 선물 id 내림차순으로 정의한 이유
선물 데이터에는 출시일 필드가 없다. 후보는 두 가지였다.

1. **firstSeenAt 기록** — 폴링에서 처음 본 시각을 저장. 첫 실행 시 모든 선물이 같은 시각을 갖게 되어 며칠간 버튼이 아무 효과가 없다. 기각.
2. **id 내림차순** — 즉시 동작. 채택.

검증 (`apps/desktop/src/data/tiktokGifts.ts`, 1889개):
- 최저 id: 핑거 하트 5487, 하트 5586, 장미 5655, 사자 6369 — 모두 초기 선물.
- 최고 id: 119996 대표님, 119711 민재 등 — 최근 크리에이터 전용 선물.
- 선물 이미지 URL 1284개에 `saliency_seg_<13자리 ms>` 타임스탬프가 박혀 있음. id와 이 타임스탬프의 피어슨 상관계수 **0.8629**.
- 타임스탬프 기준 가장 오래된 선물 id는 24k~36k대, 가장 최신은 70k~87k대.

상관계수가 1.0이 아니므로 완벽한 출시순은 아니다. 근사값으로 충분하다는 판단.

추가 확인 지점: `GiftBrowser.tsx`의 병합 로직은 TikFinity에만 있고 정적 카탈로그에 없는 선물을 뒤에 붙인다. 이들이 정의상 가장 신규다. 최신순 정렬 시 이 항목들이 상단에 몰리지 않으면 id 기준이 틀린 것이므로 재검토해야 한다.

### 수집 방식을 DOM 스크래핑에서 공개 API로 교체 (수동 가져오기 고장 확인 후)
"지금 가져오기"가 실제로 동작하는지 확인하다가 **완전히 고장난 상태**임을 확인했다.

재현: 서비스와 동일한 코드를 electron으로 직접 실행했더니 페이지(`/tiktok/obsoverlays`)는 정상 로드되는데(968KB, title `TikFinity`) 셀렉터 `.gift-card[class*="gift-card-#"]`가 **0개** 매치. 페이지 전체에 `gift` 들어간 클래스는 `giftSelect`(드롭다운) 3개뿐이고 선물 그리드 자체가 없다. 사이트가 개편된 것으로 보인다.

더 나쁜 점은 실패 방식이다. `fetchTikfinityGifts`의 대기 루프는 주석에 "최대 15초 대기"라고 써 있지만 **실제로는 타임아웃이 없다**. 카드가 안 나타나면 500ms마다 무한 재시도 → `executeJavaScript` 프로미스가 영원히 미해결 → IPC 응답 없음 → 버튼이 "불러오는 중..."에서 영구 정지, 히든 창도 파괴되지 않음. 폴링까지 켜져 있으면 주기마다 창이 하나씩 쌓인다.

해결: 네트워크를 추적해 페이지가 쓰는 원본을 찾았다.

```
GET https://tikfinity.zerody.one/api/getAllGifts?lang=ko  → 200 application/json
[{ id, name, describe, diamond_count, image: { url_list: [...] }, type, source }, ...]
```

WAF 없음. 브라우저 없이 순수 HTTP로 호출된다. 그래서 히든 `BrowserWindow` 스크래핑을 전부 버리고 이 API 한 번 호출로 교체했다.

- `net.fetch` 직접 호출 금지 규칙에 따라 `ipc.ts`의 `browserFetch`를 주입받는다. 기존 `semantleService.init(browserFetch)`와 같은 패턴으로 `initTikfinityGifts(browserFetch)`를 `ipc.ts` 초기화부에 추가했다.
- `diamond_count`를 그대로 쓴다. 기존에는 `.gift-coins` 텍스트에서 `/(\d+)\s*Coin/`을 정규식으로 뽑아 반올림했는데, 이제 원본 숫자라 더 정확하다.
- 무한 대기 버그는 구조적으로 사라졌다. 실패하면 fetch가 즉시 에러를 던지고 IPC가 `{ error }`를 반환한다.

검증 (electron main 프로세스에서 browserFetch 헤더 그대로 사용):
- `status 200`, 1.2초. 기존 방식은 페이지 로드만 9초 + 고정 대기 2초였다.
- raw 888개 → 매핑 888개, 누락 0. 이미지 URL 없는 항목 0, 다이아 0인 항목 0.
- id 내림차순 상위: 870962 Gamers' Summer, 866352 아이스크림. 하위: 5269 TikTok, 5487 핑거 하트, 5509 선글라스.
- 하위가 전부 초창기 선물로 나온 것으로 최신순=id 내림차순 근거가 한 번 더 확인됐다.

참고: API의 최대 id는 870962로 정적 카탈로그 최대치(119996)보다 훨씬 크다. 즉 정적 데이터에 없는 신규 선물이 실제로 들어온다.

### 폴링 간격을 30분으로 정한 이유
선물 카탈로그는 실제로 주 단위로 바뀐다. 짧은 주기 폴링은 신선도 이득이 없다. 그래서 "실시간"을 문자 그대로 받지 않고 다음 조합으로 구현했다.

- 간격 10분 → **30분** (`POLL_INTERVAL_MS`, GiftBrowser.tsx 상단). `ipc.ts`의 `tikke:gifts:startPolling` 기본값도 30분으로 맞춰 둘이 어긋나지 않게 했다.
- **자동 시작** — 페이지 진입 시 폴링을 켠다. 기존에는 사용자가 "자동갱신 ON"을 눌러야 했고, 이게 실제로 빠져 있던 부분이다.

수집이 API 1회 호출(약 1.2초, 210KB)로 바뀐 뒤로는 비용이 거의 없어서 간격은 CPU가 아니라 상대 서버 예의 문제에 가깝다.

### 자동 시작이 사용자 의사를 덮어쓰지 않게 한 방법
마운트마다 무조건 폴링을 켜면, 사용자가 "자동갱신 OFF"를 누르고 탭을 옮겼다 돌아왔을 때 다시 켜진다. `GiftListTab`은 탭 전환 시 언마운트되므로 로컬 state로는 기억할 수 없다.

→ `tikfinityGiftStore`에 `autoStartDisabled`를 두고, 사용자가 명시적으로 끄면 true로 표시한다. 자동 시작은 이 값이 false일 때만 동작한다. 세션 한정(persist 미적용)이며 앱 재시작 시 다시 자동 시작된다.

### 마지막 갱신 시각을 노출한 이유
`tikfinity-gift-service.ts`의 `startPolling`은 에러를 `catch {}`로 삼키고, `gifts.length > 0`일 때만 `onChange`를 부른다. 폴링이 계속 실패해도 UI에는 아무 표시가 없다. 간격을 줄여 상시 동작시키는 이상 실패가 보이지 않는 건 위험하므로, 스토어에 `lastUpdated`를 추가해 기존 상태 문구 옆에 `마지막 갱신 HH:MM:SS`를 붙였다. 서비스 쪽 에러 처리는 건드리지 않았다 (요청 범위 밖).

### 리뷰에서 나왔지만 고치지 않은 것
`handleTogglePolling`이 렌더 시점의 `tikfinityWatching`을 클로저로 잡는다. IPC 왕복 사이에 버튼을 연타하면 두 번째 클릭이 낡은 값을 보고 start를 두 번 부를 수 있다. 다만 서비스의 `startPolling`이 내부에서 `stopPolling()`을 먼저 호출하므로 타이머는 항상 하나만 남는다. 실피해가 없고 이번 변경 이전부터 있던 코드라 손대지 않았다. 고친다면 토글 버튼에 pending 상태 `disabled`를 다는 게 맞다.

### 남은 위험 / 미적용
- `useTikfinityGiftStore`에 persist 미들웨어가 없다. 앱을 재시작하면 스크랩한 선물이 사라지고, 첫 폴링이 돌아올 때까지 정적 카탈로그만 보인다. 수집이 자동이 된 만큼 이 공백이 더 눈에 띌 수 있다. 요청받지 않아 구현하지 않았다.
- 최신순 정렬은 `runtimeImages`에서 온 `Gift #<id>` 플레이스홀더도 id가 크면 상단으로 올린다. 실제 방송에서 들어온 미등록 선물이므로 신규가 맞지만, 이름이 비어 보일 수 있다.
